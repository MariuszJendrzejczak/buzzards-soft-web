**Drift diagnosis:** The one through-line risk this section had to fight was
**tier/feature-creep** — the pull to make each vivid app description *complete* by naming
the Full-tier capabilities that make it impressive (owner panel to run the schedule,
cross-device sync, push), which is exactly how the shipped `booking.body` inherited
`comparison`/`pricing`'s owner-panel line and `organizer.body` inherited the Full sync
feature. That instinct collides head-on with the Rule of One at page level: `examples`
owns *"which apps you can build and what each does for the client"*, while `comparison`
and `pricing` own *"which tier unlocks which feature"*. The fix was to hold each body at
the **Start-level end-user flow** — the concrete thing the app does for the client's
customer — and let the tier mechanics stay in their home sections. Two smaller, ordinary
drifts surfaced and were resolved in the loop: a negation reflex (*"bez zasięgu"*,
*"żeby nic nie umknęło"*) swept to affirmative (*"także offline"*, *"pomoże Ci zapanować
nad dniem"*), and two adjacent-root echoes (`schemat`→`schemat`, `przypomnienia`→
`przypomni`) swapped for a pronoun / *"da znać"*. No negation-contrast, infantile closer,
`na`-for-`dla`, migration/leave phrasing, price, or AI re-pitch appeared in the final —
the owner hard rules held throughout.

## Open Questions

*(Facts this section deliberately does **not** assert — banked rather than guessed. None
block the copy above; each is flagged because it lives at a section boundary or an
unconfirmed fact.)*

1. **Is "offline" acceptable client-facing wording, or does the owner want a plain-PL
   phrasing?** — The flowchart body uses *"a otworzysz go także offline"*. "offline" is an
   established loanword (ban-list §G2 treats *online / e-mail / SEO* as exceptions), and it
   is shorter and clearer than *"tam, gdzie zasięg bywa słaby"*. *Why it matters:* if the
   owner prefers a fully-Polish phrasing across the mobile page, this one token is where to
   apply it — it is a lexical preference, not a factual change.

2. **Booking body names owner-notification, not the owner-panel — confirm that's the
   intended Start-level framing.** — `offer-reference.md` APKA 1B (Full) shows the owner
   running the schedule from an in-app panel, and `mobile-offer-facts.md` places the owner
   admin panel in Full. This section stays Start-level (*"Każda rezerwacja od razu ląduje u
   Ciebie"* = owner notification, a Start fact). *Why it matters:* if the owner wants the
   examples cards to hint at the Full-tier owner panel as an upsell, that is a deliberate
   Rule-of-One exception to make consciously (it would overlap `comparison`), not a default.

3. **Are these three app types the final set, or illustrative of a broader menu?** — The
   intro frames them as *"trzy aplikacje, które buduję najczęściej"* and invites the
   reader's own different idea (*"Twoja może działać zupełnie inaczej"*), matching the
   reference's "materiał poglądowy" stance. *Why it matters:* if the owner intends these as
   the *only* app types offered (not examples), the intro's "najczęściej / może działać
   inaczej" framing would need to change — a positioning call, not a copy tweak.
